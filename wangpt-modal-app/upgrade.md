# Upgrade plan: lightweight REST image and Volume-backed catalog

## Summary

Split the REST control plane from the WanGP generation runtime. The public API
will run from a small Python/FastAPI image, while GPU workers will continue to
use the existing CUDA, PyTorch, WanGP, and Wan2AI image.

The model discovery catalog will be generated by an explicit Modal publisher
function and stored in the existing `wangp-data` Volume. The API will read the
matching catalog once when its container starts.

Deploying or building the GPU image alone will not publish the catalog. The
catalog publisher must run successfully before deploying an API version that
expects it.

## Why change it

The current code assigns `api_image = gpu_image`. This guarantees that
`/opt/wangp-catalog.json`, generated during the heavyweight image build, is
available to the API. However, the running API does not import or execute
WanGP, PyTorch, or CUDA. It only needs FastAPI, Pydantic, Modal, a JSON catalog,
and read-only access to generated outputs.

Separating the images will:

- Keep the public control plane small and focused.
- Remove CUDA, PyTorch, compilers, ffmpeg, WanGP, and Wan2AI from API
  containers.
- Preserve GPU worker behavior and the existing REST contract.
- Keep catalog generation tied to the exact pinned WanGP runtime.
- Make catalog/runtime mismatches explicit and testable.

The main expected benefit is architectural isolation. Any cold-start or cost
improvement should be measured after the upgrade rather than assumed.

## Target architecture

```text
                        explicit publish step
Pinned WanGP image  ------------------------------+
  CUDA, PyTorch,                                    |
  WanGP, Wan2AI                                     v
                                          wangp-data Volume
                                          /catalogs/v1/
                                          <WanGP>-<Wan2AI>.json
                                                    |
                         read once at startup       |
Lightweight REST API  <-----------------------------+
  Python, FastAPI, Pydantic, Modal                  |
                                                    |
GPU generation workers  ----------------------------+
  use the same pinned WanGP image       outputs/checkpoints/LoRAs
```

The catalog path will be immutable and derived from both runtime revisions:

```text
/data/catalogs/v1/<WAN_COMMIT>-<WAN2AI_COMMIT>.json
```

Keeping old versioned catalogs makes rollback safe. A mutable path such as
`/data/catalog.json` must not be used because two deployed revisions could then
interpret the same filename differently.

## Catalog format

Add provenance to the existing payload:

```json
{
  "metadata": {
    "catalog_version": 1,
    "wangp_commit": "92f56e5ee7227d490f6d85281c019e4c4e2dc393",
    "wan2ai_commit": "2539c3a87b64fa0f619695f02410fc92c63cba7d",
    "profile": 4,
    "attention": "sdpa"
  },
  "models": [],
  "defaults": {},
  "schemas": {}
}
```

Checkpoint availability remains excluded. It is mutable Volume state and is
already unsupported by the static `/models` endpoint.

## Implementation plan

### 1. Define and validate catalog identity

- Introduce `CATALOG_VERSION = 1`.
- Derive `CATALOG_PATH` from `WAN_COMMIT`, `WAN2AI_COMMIT`, and the catalog
  version under `/data/catalogs`.
- Extend `generate_catalog.py` to include provenance metadata.
- Add a validation function that rejects an unsupported catalog version or
  commit mismatch.

### 2. Add an explicit catalog publisher

- Add a Modal function named `publish_catalog` using the heavyweight WanGP
  image and a writable `wangp-data` mount.
- The publisher does not need an attached GPU; catalog generation already uses
  the build-time L40S capability shim and does not perform inference.
- Generate into a uniquely named temporary file in the catalog directory.
- Validate the completed payload before publication.
- Atomically rename the temporary file to the versioned final path.
- Call `data_volume.commit()` before returning success.
- Make publication idempotent: if a valid matching file already exists, return
  successfully without rewriting it.
- Reject an existing file with invalid contents instead of silently replacing
  an immutable artifact.
- Limit publisher concurrency to avoid competing commits to the same path.

### 3. Create a lightweight API image

- Replace `api_image = gpu_image` with a slim Python 3.11 image.
- Install only the API dependencies required at runtime, including FastAPI and
  Pydantic. Modal supplies the function runtime integration.
- Retain the existing read-only `wangp-data` mount used for output downloads.
- Remove the catalog-generation build command from the GPU image. Keep the
  generator script available in the heavyweight image for `publish_catalog`.

### 4. Load the catalog from the Volume

- Load and parse the versioned catalog once when the ASGI container starts.
- Validate its catalog version and both pinned commits before registering a
  ready API.
- Fail fast with a clear error when the catalog is missing, malformed, or does
  not match the deployed runtime.
- Do not reload the Volume on each discovery request. A new application
  revision uses a new immutable filename and new containers receive the latest
  committed Volume snapshot at startup.
- Preserve the existing explicit Volume reload before output downloads because
  output files are mutable and are committed by other running containers.

### 5. Update deployment documentation

The required release order will be:

```bash
cd rest-wangpt-modal-app

# Build the heavyweight runtime as needed, generate the matching catalog, and
# commit it to wangp-data.
python3 -m modal run app.py::publish_catalog

# Deploy the lightweight API and GPU generation workers.
python3 -m modal deploy app.py
```

`publish_catalog` must complete before `modal deploy`. Merely building or
deploying the GPU image does not write anything to the Volume.

When neither runtime pin nor catalog logic has changed, the idempotent publish
step should quickly confirm the existing catalog and return.

### 6. Add tests

- Catalog paths include the catalog version and both runtime commits.
- Generated catalogs contain the required provenance.
- Matching catalogs validate successfully.
- Wrong commits, unsupported versions, malformed JSON, and missing sections are
  rejected.
- Publishing an existing valid catalog is idempotent.
- The API loads discovery data from the Volume-backed path.
- Existing job submission, polling, cancellation, path validation, and output
  serialization tests continue to pass.

### 7. Verify in Modal

- Publish a catalog into a development Modal environment.
- Deploy the application and confirm `/health`, `/models`, model defaults, and
  model schemas do not start a GPU worker.
- Submit a generation job and download its output.
- Confirm API containers use the lightweight image and GPU workers retain the
  configured L40S resources.
- Compare API cold-start time and resource usage before and after the change.

## Failure handling

- **Catalog publish fails:** do not deploy the new application revision. The
  currently deployed revision and all older versioned catalogs remain intact.
- **Catalog is missing:** API startup fails with the exact expected Volume path
  in the error message.
- **Catalog metadata differs:** API startup fails rather than serving discovery
  information from a different WanGP runtime.
- **Volume commit succeeds but deploy fails:** the immutable catalog is safe to
  retain and reuse on the next deployment attempt.
- **Generation fails:** behavior is unchanged; the job ends with its existing
  structured failure record.

## Rollback

Rollback the application to the previous code and runtime pins. Its matching
catalog remains at its commit-derived Volume path, so no catalog mutation or
deletion is required. Do not remove old catalogs until no deployed or rollback
revision references them.

## Acceptance criteria

- The REST API image contains no WanGP, Wan2AI, PyTorch, or CUDA installation.
- The GPU worker image and generation behavior remain unchanged.
- Catalog publication is explicit, idempotent, versioned, and committed before
  deployment.
- The API refuses missing or mismatched catalogs.
- Model discovery does not allocate or cold-start a GPU.
- The public REST endpoints and response formats remain backward compatible.
- All automated tests pass, followed by a successful authenticated Modal smoke
  test.

## Non-goals

- Dynamically reporting checkpoint availability from the CPU catalog.
- Generating the catalog on the first `/models` request.
- Fetching catalog data from GitHub at API runtime.
- Changing WanGP generation parameters or the public job API.
- Deleting historical catalogs automatically as part of this upgrade.
